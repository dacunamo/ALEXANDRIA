01

Author filter no longer re-queries the server

donefrontend only

You asked: when you've already searched with both authors selected, switching to one author should filter instantly, not search again.

Previously, changing the author dropdown called the same search() function as pressing Enter, which re-fetched /search every time. Now a real search always fetches the full result set for the typed query (ignoring author) and caches it; changing the dropdown afterward just filters that cached array in memory.

src/web/search.jsnew state + flow
let allResults = [];   // full result set for the current query text
let lastQuery = null;  // the query that produced allResults

search()         → fetch(`/search?q=...`) → cache into allResults → filterByAuthor()
filterByAuthor() → filters allResults in memory, no network call

index.html's author <select> now calls filterByAuthor() on change instead of search(). If nothing has been searched yet, changing the dropdown is a harmless no-op.

02

Saved phrases were silently going nowhere

donebug fix

This was the most important fix in the session: POST /api/save-phrase never wrote to the database.

The handler built the phrase record, then the actual database write was commented out (//await alexandriaDB.set(...)) — a leftover from an earlier Deno KV attempt. It logged "Frase guardada!" and returned success: true regardless. Every "Guardado" you saw in the reader was a lie.

handlers/api.tssave-phrase, before → after
- //await alexandriaDB.set(key, datos_frase);
- console.log("Frase guardada!");
+ await agregarFrase(datos_frase, user.id, isPublic === true);

The other half of the bug: agregarFrase() in dbOperations.ts caught its own Prisma errors and only console.log'd them — so even after wiring it up, a failed write would still report success. It now lets errors propagate, so handlers/api.ts's existing try/catch can return a real 500 when a save genuinely fails.

03

Accounts, sessions, and a private space

donenew subsystem

The app had zero concept of a user. You asked for email+password registration, Google sign-in, and a personal space to save phrases, bookmark books, and keep notes.

Password handling

Passwords are hashed with argon2id via hash-wasm — pure WebAssembly, no native bindings, so it runs in Deno with no extra permissions. Parameters follow the OWASP baseline (19 MiB memory, 2 iterations, 1 thread).

Sessions

A session token is a random 24-byte value, base64url-encoded, handed to the browser as an HttpOnly cookie. The database never sees the raw token:

1
Generate 24 random bytes → base64url → this is the cookie value the browser holds.
2
Store SHA-256(token) as the Session row's primary key — the raw token is never persisted.
3
On each request, hash the incoming cookie and look it up by that hash. Expired rows are deleted on read.

Cookie flags: HttpOnly, Secure (only when the request came in over https:, so plain http://localhost still works), SameSite=Lax, 30-day fixed expiry. SameSite=Lax was judged sufficient CSRF protection here since the frontend only ever calls same-origin fetch() — no third-party embeds, no cross-site form posts to worry about.

Deliberately cut No sliding session renewal (expiry is fixed at creation), no password-reset UI in the first pass, no CSRF tokens beyond SameSite. All three were sized to an app with one real user — see entries 07 and 10 for how password reset actually landed.

04

Google sign-in

needs your credentials

Implemented with arctic, an OAuth2/OIDC client built purely on Web Crypto and fetch — genuinely Deno-compatible, not a Node library papered over.

→
GET /api/auth/google generates a state and PKCE codeVerifier, stashes both in a short-lived cookie, redirects to Google's consent screen.
→
GET /api/auth/google/callback checks state matches (that's the CSRF check), exchanges the code, reads the profile.
→
Matches an existing account by Google ID, then by verified email (linking the two), or creates a new user — then starts a normal session.

This one genuinely needs something from you: a Google Cloud OAuth Client ID and Secret. Steps are in entry 10.

06

Public feed, private profile

done

You wanted the existing phrases to stay public, and new saves to be private unless a user chooses otherwise.

A new isPublic column on frases_libros defaults to true at the database level — which is what made all your pre-existing phrases public automatically the moment the migration ran, with no manual backfill needed for that part. The application layer overrides that default for new saves: handlers/api.ts only sets isPublic: true when the client explicitly asks for it, so a fresh save without that flag lands as private.

EndpointAuthReturns
GET /api/frasesnone — publicEveryone's phrases marked isPublic: true
GET /api/my-frasesrequiredAll of your phrases, public and private

/frases dropped its login redirect — anyone can browse it now. Mi Espacio's "Mis Frases" section switched to /api/my-frases and shows a 🔒 Privada badge on anything not public. The highlight-and-save flow in toolbox.js now asks, via a confirm dialog, whether the new phrase should be public before saving it.

07

Show/hide password, and getting back in

done

A small eye toggle (src/web/passwordToggle.js) sits inside every password field on /login and /register — click it to reveal or re-hide what you typed. It's one tiny script wired by a shared .password-toggle class, not duplicated per page.

For the actual "I forgot my password" problem: rather than build a full self-service email flow (which would need an email-sending service configured first — a real prerequisite, not yet in place), you chose the lighter option for now.

resetPassword.tsrun by hand, no email needed
deno run -A --env=.env resetPassword.ts <email> <new-password>

It hashes the new password with the exact same hashPassword() used at registration (now exported from handlers/auth.ts so both places share one definition of "how we hash"), updates the account, and deletes that user's existing sessions so the new password takes effect immediately.

09

Dependencies and database migrations

doneno data loss

Two packages were added to deno.json: hash-wasm (password hashing) and arctic (Google OAuth). Cookies use Deno's own std/http/cookie.ts — no third package needed there.

The one real risk in this session Your database had real saved phrases but no Prisma migration history — it had been set up with db push, not migrate dev. Running migrate dev blind on a database like that is exactly the situation where Prisma can offer to reset it. Before touching the schema, the current structure was captured and marked as an already-applied baseline migration (0_baseline), so every migration after that only ever added things — nothing was dropped or reset, and this was verified with prisma migrate status before and after.
